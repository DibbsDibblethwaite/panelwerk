## The rule the cure gives `zoom` (Ian, 2026-11-26, ZOOM-DRIFT-CURE)

Panelwerk keeps no behaviour rules of its own (each consumer's panel rules name the zoom: Kör's and Fläns's B-PNL-6 and 7, Rödalog's B-PNL-41 to 44, Klinga's B-PNL-6, 7 and 13); the module's documentation says how `follow` works. The design's wording for it (§4), approved with the card, is what W-D1 builds:

> A size the host gives on the frame after the panel asked for one (its opening size, a new zoom's size), within a quarter second, is the host's answer: never a new zoom, never asked again. A plugin that pairs requests and answers itself says so, and then the panel awaits nothing. A menu choice is told to the plugin once the window has taken it; if the window is back at its old size, or the plugin reports a refusal, the zoom goes back and nothing is told. Any other size the host gives is the host's own: the zoom follows it.

With the fact-check's correction (its finding 1, the design's change 1): the panel awaits an answer only when the window must change size, so a followed corner-drag step, whose window already has the new zoom's size, awaits none and no drag step is lost.

With the window part (the design's (B); Ian, 2026-11-26, ZOOM-DRAG-STEP, points 1 (a) and 2 (a); the design's amendment of that date):

> While the main mouse button is held, a size the host gives is a drag: followed, never taken as an answer. A corner-drag step that lands before the previous step's zoom has drawn is not overwritten: the panel's request for the previous step's size does not reach the host.

Without the window part (Kör and Fläns on the shared part alone), neither: a drag step within `ANSWER_WITHIN` after the panel asks the window back to its shape is that request's answer, and a step landing before the previous step's zoom has drawn is overwritten by the request for the previous step's size, as in v0.5.0.

## v0.6.0, in series

- [x] **W-D1 The shared zoom code** (design (A); 1.0): `zoom::follow` never takes the host's answer to the panel's own request for a new zoom and never asks for it again (at most one request per zoom); the wait for an answer bounded at a quarter second of egui's input time, a named constant; a menu choice told to the plugin only once the window has taken it, and undone, untold, when the window is back at its old size; any other host size the host's own, followed and passed to `ZoomHost::zoom_followed` (default: `zoom_chosen`, v0.5.0's reading); `ZoomHost::answers_paired` (default false) for a consumer whose window code pairs requests and answers ((B)), so `follow` awaits nothing; `zoom::refused(ctx)` for (B) to call on CLAP's `false`. Ends with: the hook, 100 % coverage.
  - *As built (2026-11-26, branch `zoom-drift-cure`, 3248385; not reviewed yet):* as the design, with these differences. `ANSWER_WITHIN` is public, so the tests drive egui's clock by it and W-D3 can pair within the same constant. The window's size is worked in pixels from egui's screen × the zoom × the display's scale, since on the pass a new zoom takes effect egui gives the last pass's screen rescaled (egui 0.37 `Context::begin_pass`), not the window: that is why the prototype's `near(now.screen, base)` was right on that pass. `zoom::refused` undoes only a menu choice waiting on its answer; for any other refused request it only stops awaiting the answer. A choice is judged (told, or undone if the window is back at its old size) on the first pass after its request, however late; only following a size depends on `ANSWER_WITHIN`. The tolerance for "the same window" is half a pixel (`HALF_PIXEL`); v0.5.0's half-point tolerance for following a host's size is kept, named `OFF_SIZE`. Tests: `crates/panelwerk-panel/tests/zoom_answer.rs` (12), with a model of egui-baseview and the host; `tests/zoom.rs`'s refusal test given one set-up pass (the second pass is the opening's answer).
